## 一、目的与范围

界定本项目的**配置项**（哪些产物受版本控制与变更控制）、**基线**（哪些组合被冻结为可回溯的节点）与**变更入口**（改动走哪条路径）。

**不管**：具体提交格式与分支命名 → [`git-conventions.md`](../git-conventions.md)；产品排期不在本文件管辖。

## 二、配置项识别

| 类别 | 路径 | 版号形态 | 变更入口 |
|---|---|---|---|
| 客户端代码 | `app/` | 无独立版号，随产品版本 | PR → `main` |
| 服务端代码 | `server/` | 无独立版号，随产品版本 | PR → `main` |
| 内容源数据 | `content/` | **内容包 tag** `pack/<space>/vX.Y.Z` | PR → `main`，发布打 tag |
| 基础设施 | `infra/` | 无独立版号 | PR → `main` |
| 活文档（含原交付物文档） | `docs/specs/` `decisions/` `intent/` `runbooks/` | **不设版号**（以 `git log` 为准） | PR → `main` |
| 仓库级约定 | `.github/` `.gitattributes` `.gitignore` | 无独立版号 | PR → `main` |

> **为什么原「交付物文档」行并进来了**：`SCMP` `SRS` `SDD` `STP` `STD` 五份已由 [`decisions/0009`](../../decisions/0009-deliverables-dissolve.md) §5.1 迁入 `docs/specs/`。此前它们单列一行「`docs/deliverables/` → `vX.Y.Z` 独立递增」，两行指向同一批文件、却给两套版号结论 —— 合并成一行。
>
> ⚠️ 这五份正文末尾的「历史（迁移前版号序列）」节，记的是**迁移前**的版号序列（用于与旧版交付物对账），**不是现行版号**。现行版号不存在，以 `git log` 为准。

**三条识别判据**：

1. **生成物不入库**：`content/*/dist/` 由 `content/tools/build.py` 本地构建，`.gitignore` 覆盖，CI 有判据（见 `../.github/workflows/content-checks.yml`）。
2. **内容包版本与代码版本解耦**：内容包打 tag，不打产品 tag；递增**按「是否让既有进度失效」判**（删项 / 改 `Item.id` / 改 `⪯` = major），不按提交类型判。
3. **活文档不设版号**：手写「最后更新」头会变成第二份会过期的记录。

### 3.3 基线之间的增补判据

| 情形 | 处置 |
|---|---|
| 新增基线未覆盖的配置项 | 新开基线编号，**不修改旧基线** |
| 旧基线的配置项内容变更 | 走变更控制（§四），记入新基线 |
| 旧基线的记录本身有误（勘误） | 可原地修正，但须在修订历史写明「勘误」及原文 |

**为什么不允许回溯改旧基线**：基线的作用是「给未来一个可回溯的节点」。允许回溯修改，基线就退化成「当前状态的快照」，而当前状态本来就有 `main` 可查。

### 5.2 状态一览的维护责任

本表**不是自动生成的**，每次交付物版号变化须手工更新。这是刻意选的：

| 方案 | 问题 |
|---|---|
| 手工维护本表（现状） | 会滞后，但滞后是可发现的（与各文件**历史节的最大版号**对不上） |
| 脚本扫各文件头部自动生成 | 各文件头格式必须高度一致，且版号一改就要重跑；CI 会因此需要写权限 |

> **口径变更（`S7-1`）**：原先「滞后是可发现的」依靠「与各文件**头部**对不上」—— 五份迁入 `specs/` 后头部不再有版号，该依据改为「与各文件**历史节的最大版号**对不上」，与 §5.1 表下注、`D2` 三者同一口径。依据换了，结论（仍手工）不变。

**判据**：本表滞后属**已知代价**，不是缺陷。若将来**表内文件全部写实**、版号变动频繁，再改成脚本生成，届时本表降为「生成物的说明」而非权威处。（此处刻意不写份数 —— 份数随出仓与骨架删除在变，而「要不要改脚本」只看「还有没有骨架」这一个条件；写死一个数只会每次都得回来改。）
