# 软件测试计划（STP）

> **状态**：§五 合计 **1020** 条。
> 本文件规定**测什么、怎么判通过**。用例正文在 [`STD`](std.md)；实际执行结果在 `weltuhr-knowledge-docs` 的 `records/`，**§六 是当前读数**。
> **追溯补录**：2026-10-17 · §五 §六 依据 `app/test/` 与 `content/tools/` 的既有测试反推，非当时所写。

## 一、测试分层

| 层 | 范围 | 命令 | 跑在哪 |
|---|---|---|---|
| 单元测试 | 纯函数与算法（`fold` · 定位 · 量化 · `⪯` 校验 · 构图与投影） | `flutter test` | 本机 + CI |
| 组件/Widget 测试 | 视图投影、状态变化、交互 | `flutter test` | 本机 + CI |
| 内容管线回归 | `content/tools/` 的校验器与构建器 | `python content/tools/verify.py --suite` | 本机 + CI |
| 架构约束 | 跨层依赖、字面量常量等**机械化**约束 | `dart run tool/lint/check.dart` | 本机（CI 待接入） |
| 端到端 | 五动作闭环（加载 → 圈定 → 建 Plan → 学一项 → 判合格写事件） | 手工 / 集成 | 本机 |
| 真机与制品 | 三端安装包可装、可启动、能加载内容 | 手工 | **用户终端** |

**分层判据**：一层能测的，不靠下一层兜底。凡可写成断言的，不得写进「手工验收清单」—— 手工清单只留**断言写不出来**的项（观感、真机行为、商店审核）。

## 二、环境

| 环境 | 能跑什么 | 不能跑什么 |
|---|---|---|
| 本机（开发机） | analyze · test · 内容管线 · git | — |
| CI（`content-checks`） | 内容管线四步 | 客户端测试（尚未接入） |
| 沙箱 / 代理环境 | 只读操作 | `flutter build` 三端 · `flutter run` · 签名打包 |
| 用户终端 | 三端构建 · 真机 · 制品验收 | — |

**未验项处理**：跑不了的项在 `STR` 里标「未验 + 原因 + 归谁验」，**不得留空、不得写「应该能过」**。

## 三、通过判据

| 项 | 判据 |
|---|---|
| 静态检查 | `flutter analyze` 零 issue；架构约束规则零违规 |
| 测试 | 全部用例通过；不允许「已知失败但先合」 |
| 内容管线 | `content-checks` 四步全绿（fixtures 回归 · 确定性 · 构建 · 产物不入库） |
| 覆盖 | 每个 `SPEC-*` 至少一条可观测断言（`X-05`：验证不得自证） |
| 帧率 | `C-32` 三档（合成 ×1 / ×2 / 真实 α 包）在 `C-33` 基准窗口（`1920×1080` 客户区）下均达**优线**。**不进测试套件**：`FrameTiming` 只在真机产生，判据归终端 `flutter run --profile`（口径见 §八） |

### 5.2 一条已修正的判断

`v0.3.0` 这里写的是「事件只 append、UI 不写状态这两条**靠接口形状保证，不设 lint**」。`R-08` 核对后改判 —— 形状挡得住**改**，挡不住**加**：

| 约束 | 「形状保证」阻止了什么 | 形状**没有**阻止什么 | 现在的机制 |
|---|---|---|---|
| 事件只 append | 阻止**修改**已有事件（无 `copyWith`、字段 `final`） | 阻止**新增** `copyWith`、加可变字段、给 `EventStore` 加 `delete` —— 加了不会有任何东西报错 | `R3`（`TC-INF-011`–`015`） |
| 源不进视觉通道 | 源在核心层流转，不被当作渲染数据 | 阻止视图层顺手把源收进构造参数 | `R4`（`TC-INF-016`–`019`） |

**「UI 不写状态」不在此列** —— 它写不成静态规则（判据是「有没有并行的可写状态」，属结构性质而非文本模式）。`v0.6.0` 起它的**核心层半边**已有断言（`TC-EVT-014` / `026` / `027`：状态只能由 `fold` 从事件算出，`FoldedState` 只读），故移出 `STD` §4.3 的 B 类；**UI 半边仍无断言** —— `v0.8.0` 建的是 spike 页面（`TC-VIEW-037` / `038`），它持有的是**帧时序读数**（`ValueNotifier<HudSnapshot>`），不是知识状态，所以没把这一项销掉。已登记进 `STD` §五 待补。

**帧率不在这张表里，也不是漏了**：`C-32` 的 30 / 50 fps 只能在真设备上量 —— headless 测试环境不产 `FrameTiming`，在测试里断言 fps 等于造一台跑不起来的机器。`TC-VIEW-025`–`030` 锁的是**时序算法**（中位 fps、p95 帧间隔、窗口裁剪），判据本身归终端 `flutter run --profile`。同理 `TC-VIEW-019`–`024` 锁的是**绘制调用数**，不是绘制耗时：调用数是代码属性，耗时是设备属性。

区别在于：C 类是「测了但没标号」，补个编号就行；B 类是「根本没有东西会响」，得补机制。`R-08` 只补了**能写成静态规则**的两条，写不成规则的那部分要靠断言，仍归后续批次。

## 六、错误码覆盖

`content/tools/validator.py` 共定义 **37 个错误码**（`v0.2.0` 记 36，实测少记 1 —— 那次统计用裸正则扫全文，把注释里提到的码当成定义）。截至 2026-10-17 **37/37 全部有 fixture 断言**：

| 层 | fixture | 覆盖的码 | 为什么分两层 |
|---|---|---|---|
| 源数据层 | 32（9 原有 + 23 新增） | 31 | 走 `build_text`：读源 → 校验 → 产物层的完整链路 |
| 产物层 | 8（全新增） | 6 | `assemble()` 拼出的 pack 结构恒定，`E-PACK-*` / `E-META-*` 在源路径上**结构上不可达** |
| **合计** | **40** | **37** | |

### 6.1 这 31 个码为什么以前没测

不是「忘了写」，是**没有机制提醒**。原 9 个 fixture 是「想到一条写一条」的产物，负例只覆盖了最早实现的那批规则；后来加的 `E-DOMAIN` / `E-SCHEME-AUTH` / `E-EXCERPT-FIELD` 等再没配负例，而**没有任何东西会因此变红**。

所以本次处置不是只补 fixture，而是把「覆盖对账」做成 `--suite` 的一层（`v0.9.0` 起是第三步；其后还有 §七 的输出可移植性）：

```
— 错误码覆盖 —
错误码覆盖：37/37
```

定义集与断言集差任何一条即失败。两个方向都查：**定义了没断言** = 那条规则从没被执行过；**断言了没定义** = `expect.json` 里写了 typo，永远不可能满足。没有这一步，补 31 个 fixture 只是把同一个坑填一次 —— 下一个新增规则照样会漏。

### 6.2 6 个码在源路径上不可达 —— 不当作死码

`E-PACK-TYPE` / `E-PACK-EXTRA-KEY` / `E-PACK-MISSING-KEY` / `E-META-FIELD` / `E-META-EXTRA-KEY` / `E-META-VERSION` 在 `assemble()` 之后**永远不触发**：拼出来的 pack 必然五段齐全、`meta` 必然只有 `space` 与 `version`。

它们不是死码，防的是两件真事：**有人手改产物**（`verify.py --pack` 直接读外部文件）与**构建逻辑退化**（某天 `assemble()` 真的丢了一段）。故单列 `fixtures/pack/` 产物层测试，把坏对象直接喂给 `check_pack_object`。

> 判据：**「在当前调用路径上不可达」≠「没有价值」**。要先问清它防的是什么场景，确认那个场景不存在了才删。

### 6.3 覆盖率的边界，要说准确

37/37 证明的是**每条拒绝路径都执行过一次**，不证明「负例代表真实坏法」。这 31 份负例全部由 `valid-min` 变异得出，而 `valid-min` 是最小样例 —— 真实内容包的坏法与它并不完全同构。

`v0.2.0` 那句「等 α 包落地再同批补」在这个维度上仍然成立：α 包（`B2`）落地后**应补真实坏法样本**。届时新增的是「更接近现实的负例」，不是「补上没测的码」—— 两件事别混。

> `R-07` 的「已规避」指**机制层**已闭环（不会再静默漏），不指「负例质量已达标」。

## 七、输出可移植性

`--suite` 的第四层（`v0.9.0` 新增）。前三层的判据都要**真的跑一遍**才算数，这一层守的失败恰好跑不出来：`print` 一个 cp936 编码不了的字符，在 UTF-8 环境（CI 是 `ubuntu-latest`）**永远不触发**。所以只能静态查 —— 扫 `content/tools/*.py` 的 AST，运行期字符串字面量里出现 GBK 编不了的字符即失败。

### 7.1 起因是一处真实故障

`build.py` 用 `✓`(U+2713) / `✗`(U+2717) 做输出前缀。这两个字符不在 GBK 内，Windows 中文控制台（cp936）`print` 时抛 `UnicodeEncodeError`。后果有两层，第二层更糟：

| 面 | 后果 |
|---|---|
| 构建成功也报错 | `build()` 已写盘，崩在随后的 `print` ⇒ 退出码 1 + traceback，**产物是好的**却被读成失败 |
| 报错路径也崩 | 失败分支同样用 `✗` 打头 ⇒ 源数据真有问题时，用户看不到是哪一条，只看到 `UnicodeEncodeError` 盖在上面 |

同一轮还发现第二处：`check_determinism` 的子进程调用假定 `proc.stderr` 一定是 `str`。当子进程用系统代码页写字节时，解码在 CPython 的 `_readerthread` **后台线程**里失败 —— 那个 `UnicodeDecodeError` 死在子线程、主线程收不到，`proc.stderr` **静默变成 `None`**，于是 `.strip()` 抛 `AttributeError`，把「子进程为什么挂」彻底埋掉。

修法三层，缺一层都不够：

1. 子进程 `env.pop("PYTHONIOENCODING")` + `PYTHONUTF8=1` —— 前者的优先级**高于**后者，不摘掉就白设；
2. 父侧 `errors="replace"` —— 兜住任何仍写出非 UTF-8 字节的子进程；
3. `proc.stderr or proc.stdout or ""` 判空 —— 前两层失效时不至于把诊断变成 `AttributeError`。

### 7.2 判据边界

- **只查 AST 里的字符串字面量**：注释不进 AST（本来也不会被打印）；模块 / 类 / 函数的 docstring 显式跳过。
- **判据是 GBK 而非 ASCII**：中文输出是本项目常态，按 ASCII 判会把每个汉字都算成违规。
- **报错信息自身必须可打印**：报 `✓` 违规的那一行若含 `✓`，会在同一个控制台上再崩一次 —— 故坏字符一律转义成 `\uXXXX`。

这一层不产生 `TC-` 用例：它不是「某条 `SPEC` 的行为」，而是工具链自身的健康约束，与 §六 的覆盖对账同类，故 §5.1 的 211 条不含它。

> 适用范围只到**工具链输出**。应用侧文案走 Flutter 的字体渲染，与此无关。

## 八、帧率判据的测量口径（`C-32` / `C-33`）

### 8.1 为什么它不在测试套件里

`FrameTiming` 只在真实设备上产生。headless 环境拿不到光栅线程的耗时，在那里断言 fps 等于自制一台跑不起来的机器。故 `C-32` **不进 `flutter test`**，只在终端 `flutter run --profile` 下判。

`TC-VIEW-025`–`030` 守的是「拿到时序之后怎么算」—— 中位与 p95 怎么分、样本不足怎么办、切档清不清窗口。它们与「实际跑出多少」是两件事，谁都不替谁作证。

### 8.2 判据必须带窗口前提

光栅成本随覆盖面积上涨。`STR` 轮次 `R1` 有一次受控对照：同一份 `合成 ×1`、点数与几何不变，只把窗口从 `1584×875` 放到 `1920×1109`（面积 `1.55×`），光栅 p95 从 `5.70 ms` 涨到 `11.51 ms`（`2.02×`）—— 占帧预算从 43% 升到 **88%**。

⇒ **同一档能读出「余量 57%」和「占预算 88%」两种结论**。判据不写窗口尺寸，就等于允许任何尺寸被解释成通过。故新增 `C-33`（基准窗口 `1920×1080` 客户区），`C-32` 只在它名下解释。

### 8.3 读数要三项，缺一项都会误判

| 读数 | 承载什么 | 缺了会怎样 |
|---|---|---|
| 中位 fps | 稳态 | 只看平均，会把「稳定 45 fps」与「60 fps 但每 5 帧掉一次」判成同一件事 |
| p95 帧间隔 | 卡顿 | 中位好看、p95 是它的 1.8 倍时，体感已经明显变差 |
| 光栅 p95 占预算 | **距阈值多远** | 只看「是否 ≥50」会把 88% 与 43% 都记成「通过」，下一次改动直接掉出优线而无预警 |

### 8.4 装置与读数的行格式（`B17a` 笔 6 起）

**装置分两半，缺一半读数就不可复跑**：

| 半 | 落点 | 它管什么 | 怎么验 |
|---|---|---|---|
| 算法 | `app/lib/core/bench/frame_stats.dart` | 三项读数怎么算：中位帧间隔取倒数得中位 fps、p95 帧间隔、光栅 p95 ÷ **中位帧间隔** | `flutter test`（9 条，`TC-INF-043`–`052`） |
| 采集与行格式 | `app/tool/bench/` | 固定剧本跑真机、把读数写成一行 `FRAME_BENCH {…}`、并能原样读回 | 行格式 `flutter test`（2 条）；采集只 `analyze` —— ⚠️ **这一条不够**：`flutter analyze` 在分析器的 `FfiVerifier` 崩掉时照样报 `No issues found` 并以 0 退出，动了 `dart:ffi` 的文件须另跑单文件 `dart analyze` 或 `dart compile kernel`（实证见 `STD` §3.70）；读数归终端 |

- **「占预算」的分母是中位帧间隔**，沿用 `STR` 轮次 `R1` 那张表的写法，不改成 `1000 / frameTargetFps`。换分母会让新读数与 `R1` 不可比，而 `R-22` 要的正是「同一口径能重跑」。⚠️ 这个分母**自指** —— 帧变慢时中位间隔一起变大、占比反而下降，所以本项必须与中位 fps 并读，不能单独当「有余量」的证据。
- **基准窗口由装置自己回写、自己判**：装置拿不到窗口就改尺寸（那要平台插件），所以它把实测客户区尺寸写进读数行，`premiseOk` 由尺寸现算；`false` 不等于跑挂了，等于「这组数不能按 `C-32` 的 30 / 50 解释」。
- **派生的判断不进读数行**：行里只有「量到了什么」（场景 · 窗口 · 六项读数），`meetsTarget` / `meetsGood` / `premiseOk` 都是 getter。派生值一落盘就多一份会与读数矛盾的副本。
- **固定剧本**：地址取**行集合最大**的那一层（`core/bench/bench_address.dart`，贪心：每一步在子节点里挑以它为地址时行数最多的那个，行数靠 `treeOutline` 现算），列表以固定周期匀速扫过整个可滚动范围。选滚动不选「点开一级」是因为帧率是**稳态**读数，一次性交互只产生两三帧。
  - ⚠️ **不能用「沿第一条子链下钻到底」**：`treeOutline` 只沿选中路径展开（`SPEC-TREE-003`），学科轴第一个门类下只有一个一级学科，沿它走八级累计不到二十行 —— 在一屏三十几行的视口里根本不滚，装置跑满二十秒只报「可滚动范围是 0」。这条判据的首版就写成了「沿第一条子链」，2026-10-26 真机实测才撞出来。
- **尺寸一律按物理像素**：`C-33` 指物理客户区（`ADR-0002` 修订三），判定与读数都读视口的 `physicalSize`，**不读 `MediaQuery.sizeOf`**（那是逻辑像素）。两者在 100% 缩放下恰好相等 ⇒ 这个错在那种机器上永远看不见；换到 125% 缩放的机器，逻辑宽 `1536` 永远够不到基准 `1920`，装置安静等到超时。读数行因此把 `physical*` 与 `logical*` 两套都存下来（`schema: 2`），旧版行拒收 —— 旧行的 `width` / `height` 是逻辑值，按新口径读就会得出「不达标」这个错误结论。
- **窗口由装置自己设，设完还必须提到前台**：`tool/bench/window_fit.dart` 用 `EnumWindows` 枚举**本进程**的可见顶层窗口，把它改成 `1920×1080` 物理的无边框客户区（无 `WS_CAPTION` 时客户区等于窗口矩形，不必反算边框），再 `ShowWindow(SW_RESTORE)` + `BringWindowToTop` + `SetForegroundWindow`。**人手拖不出来**：客户区宽 `1920` 只有最大化才有，高 `1080` 只有非最大化才调得出，两个条件互相排斥。设不上就退回老路并说清原因，读数标 `premiseOk=false` —— 前提失败不假装成测量结果。
- **绑定是设窗「前提的前提」，且失败必须分步说清**：每个符号的**宿主 DLL** 要对（`GetSystemMetrics` 属 `User32.dll`，`v0.80.0`–`v0.80.1` 写成了 `kernel32`），而 `_Win32` 的构造是「要么全成、要么全废」—— 一个符号错库即整段设窗静默失效，连 `EnumWindows` 都执行不到。故 `fitBenchWindow` 返回带环节名（绑定 / 找窗口 / 改尺寸）与原始错误文本的结果，调用方**不许**再自行补一句猜的原因：三跑三版的日志分别写成「前台不是本进程的窗口？」「枚举不到本进程的可见顶层窗口？」，两次都把排查引向别处。**窗口摆原点，不居中** —— 居中要先查屏幕尺寸，那一步正是这次的死点，纯装饰却换来一个能把整段设窗吞掉的绑定。
  - ⚠️ **取句柄不能看谁在前台**：首版用 `GetForegroundWindow`，而装置是从终端 `flutter run` 起的 ⇒ 前台永远是终端，一次都拿不到本进程的窗口。日志写成「前台不是本进程的窗口」，把「窗口在后台」说成了「窗口不存在」。也没走 `FindWindowW` 按 `FLUTTER_RUNNER_WIN32_WINDOW` 找 —— 那要拼 UTF-16 串并依赖 runner 的私有窗口类名，Flutter 升级改名就静默失效。
  - ⚠️ **不提前台就是零帧**：尺寸设对但窗口留在后台时，Windows 判它被遮挡、引擎跳过光栅，`FrameTiming` 根本不产生 —— 实测 20 秒采样 **0 个帧间隔**，而装置报的是「样本不足」，那句话把人引向采样时长。同一处「设窗」的两个失败都只会以「等超时」与「样本不足」的面目出现，都不会被任何用例拦住。
- **开测前先等基准窗口**：装置装完包不直接预热，而是每 200 ms 看一次视口 —— 进了 `C-33` 基准就开测，最多等 90 s，到点仍不是基准就照测并把 `premiseOk` 标成 `false`。判据在 `core/bench/bench_gate.dart`（`TC-INF-054`–`057`），装置只管把答案说给人听（界面上显示当前尺寸与剩余秒数）。**「等」是耐心不是判据**：到点照测不让一次真机运行白跑，但也不假装那组数可以按 `C-32` 读。
- **读数行写开测那一刻的尺寸**，不写「出读数时」的尺寸：采样跨 20 s，中途拖窗口会让一段跨两个尺寸的样本标成单一前提。中途真变过就在 `stdout` 另起一行警告，不塞进读数行。
- ⚠️ **装置不在 CI**：CI 里跑只能得到「样本不足」，那不是判据。

### 8.5 本轮结论与未验项

四组读数与成本模型见 `STR` 轮次 `R1`（已出仓，**不在此复制**）。未验项也记在那里：`macOS` / `iOS` 帧率、4K 与更大窗口、DPI 缩放实际取值、长时间运行稳定性 —— 各自的归属与验法见表，不得留空。

> 一条副产品：本轮确认**批绘制对瓶颈无效**（同面积下线段数差 3 倍，光栅只差 9%），`ADR-0002` §决策 2 的对应手段已随之改判，见该 ADR 修订二。
