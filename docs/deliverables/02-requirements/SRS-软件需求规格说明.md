## 三、`v0.1.0` 需求切片

### 3.1 切片规则

| 项 | 规则 |
|---|---|
| 粒度 | 按 `SPEC-*` 单条切，不按文档切（一份设计文档通常横跨多个版本） |
| 入切片判据 | 该条是「学习主链五动作闭环」的必要条件：加载空间 → 圈定目标 → 建 Plan → 学一项 → 判合格写事件 |
| 不入切片的三类 | ① 笔记与治理（`P2`）② 上架与分发的非功能约束（`P3`）③ 服务端与跨设备合并（`P4`） |
| 挂载内容 | 编号 + 一句需求陈述 + 验收指向 |
| 编号写法 | 表格内省写 `SPEC-` 前缀（`FND-001` = `SPEC-FND-001`），与各设计文档验收表的写法一致；需要绝对无歧义时写全称 |
| 不写什么 | 判据理由、参数数值、算法细节 —— 全部回指，不复制 |
| 完整性 | 不得出现未在 `00-index.md` 登记的编号；切片集合 ⊆ 203 条全集；同一编号只归一个版本 |

### 3.2 判定结果

**141 / 203 条进 `v0.1.0`**，占 69.5%。这个比例偏高，原因是设计基线按「完整主链」一次写透：

- `FND` / `VIEW` / `STEP` / `QUANT` 四域**几乎整体**在主链上 —— 地基、视图、习得、量化本身就是主链的四个面，拆出一部分反而会让每条都失去意义。
- `PACK` 只有 overlay 与版本迁移（7 条）不进主链：前者依赖提交通道，后者要等第二个包版本。
- `NOTE` **整域 19 条全部不进** —— 笔记是派生产物（`NOTE-001`），主链五动作不依赖它。
- `GOV` 只有 3 条进后续版本：2 条跨设备合并、1 条降级态。
- `ACC` 进 12 条 —— 账号为使用前提（`ACC-001`），登录链在 `v0.1.0` 必须成立；不进的三条都依赖验证渠道或第二台设备。
- `SYNC` **整域 16 条不进** —— `v0.1.0` 只需「能登录」，不需要把事件搬到另一台设备。

| `GOV-010` | 全序来自 HLC，不用服务端递增序号 | 离线可写的理由是 `v0.1.0` 的，但「全序在双端成立」只有第二台设备才能验 |
| `GOV-011` | 同一项被两台设备都学了一遍：两个序列都重放，不去重 | 同 `GOV-010`；去重只针对同一条事件重传，与跨设备合并是两件事 |

> `v1.1.0` 只有 2 条，**不是切片遗漏，而是需求基线的边界**——见 §五 ②。

## 五、基线缺口与待办

**这四项都是核对过程中实测出来的，不是推测。** 前三项属 `design/` 基线自身的缺口，第四项属排期风险。

### ① 验收表覆盖 100 / 203，`FND-016` 在自己的域里就没被满足

`FND-016` 要求「每条裁定至少被一条验收行覆盖」，实测：

| 域 | 有验收行 | 无验收行 | 覆盖率 |
|---|---|---|---|
| `FND` | 6 / 16 | **10** | 38% |
| `VIEW` | 16 / 35 | **19** | 46% |
| `PACK` | 9 / 18 | **9** | 50% |
| `PLAN` | 10 / 21 | **11** | 48% |
| `STEP` | 14 / 34 | **20** | 41% |
| `QUANT` | 11 / 15 | **4** | 73% |
| `NOTE` | 11 / 19 | **8** | 58% |
| `GOV` | 7 / 14 | **7** | 50% |
| `ACC` | 8 / 15 | **7** | 53% |
| `SYNC` | 8 / 16 | **8** | 50% |
| **合计** | **100** | **103** | **49%** |

**怎么读这个数字**：验收表的行数按「断言」而非「裁定」计（`FND-016` 自己也写明「行数与条目数不作等式」），所以有验收行的条目不等于测了，无验收行的条目则**一定没测**。103 条属于后者。

**与 `STD` §四 不是同一口径，不要混用**：

| 口径 | 数字 | 问的是 |
|---|---|---|
| 本表「有验收行」 | 100 / 203 | **设计侧**：这条裁定在 `design/` 里有可观测断言吗 |
| `STD` §四「有用例」 | 18 / 203（新增两域 0 条） | **实现侧**：这条裁定在 `app/test` 或管线 fixture 里有对应用例吗 |

两个数都小，但结论不同：前者是「断言没写」，后者是「测试没写」。有验收行也可以无用例（如 `FND-002` 只设计了向量、未实现校验器用例），反之亦然。

**为什么不全补**：补验收行不是写文档，是**把每条裁定还原成一个可构造的测试向量**。写不出向量的条目说明它本就没想清楚（`FND-016` 原话），应退回补设计。这件事应随批次推进逐批做，不在此处一次性伪造。

**处置**：每批开工时，该批承接的 `SPEC` 若有「无验收行」，须在 PR 里补向量或明确标注「本批不验，理由」。本文件 §三 的 ⚠ 标记即为该清单。

### ② `v1.0.0` / `v1.1.0` 各只有 2 条，与工程量严重不匹配

`P3` 上架与分发（商店审核材料 · 更新机制 · 分发渠道）、`P4` 服务端与跨设备（部署 · 同步 · 私有化交付包）在两版合计只有 **4 条**需求条目，而这两阶段的实际工作量远超此数。

**根因**：`design/` 八份文档全部是**客户端**设计基线 —— 服务端、制品、分发、更新机制**没有对应的设计文档**，因此没有 `SPEC` 条目。

**这不是切片错误**，但必须记下来：`P3` / `P4` 开工前需要一份**服务端与分发设计基线**（至少覆盖部署形态、同步协议、更新通道、私有化边界），否则这两阶段没有需求可承接，验收只能凭「做完了」判断，正是 `FND-016` 要禁止的形态。

### ③ `PACK-018` 与 `SDP` `B8` 的路径策略冲突

| 出处 | 表述 |
|---|---|
| `PACK-018` | 客户端 `PackLoader` 按**运行期 CWD** 查找 `<仓根>/content/<空间>/dist/pack.json` |
| `SDP` §4.2 `B8` | `PackLoader` **改为 exe 同级解析** |
| `SDD` §3.2 | 本项目选 exe 同级；且该方案在 App Store 形态下不成立 |

`PACK-018` 描述的是**开发期现状**（`flutter run` 须在 `app/` 下跑），`B8` 描述的是**制品期目标**。两者不必然矛盾，但规格里只写了前者 —— 照规格实施，`B8` 会变成「违反 `SPEC-PACK-018`」。

**处置**：`PACK-018` 须改写为「开发期按运行期路径查找；制品期按制品同级查找，两者共用同一解析器」，属 **B 级变更**（改行为语义），走 PR + 变更说明。**建议在 `B2` 写加载器时一并做**，因为那时正好要把「路径探测」与「解析」拆开。

### ④ `TBD-9`（`C-28` 搜索模糊阈值）在 `v0.1.0` 关键路径上

`TBD-9` 与 `C-28` 属 `VIEW` 域（快速定位），而 `VIEW-024`–`VIEW-033` 整组都在 `v0.1.0`。ADR-0002 已定「快速定位开工前须实测标定」，但标定需要**真实内容包**。

**处置**：`C-28` 的标定挂靠 `B2`（α 真实内容包落地）之后、`B3`（三视图 + 快速定位）开工之前，**不得给默认值**（「给 TBD 常量补默认值」是最典型的越界贡献）。
