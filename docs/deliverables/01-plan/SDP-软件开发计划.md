## 四、进度与里程碑

### 4.1 总计划（阶段级）

| 阶段 | 里程碑 | 关键内容 | 目标版本 | 出口判据 |
|---|---|---|---|---|
| **P1** | 学习主链贯通 | 三端骨架 · 事件内核 · α 内容包 · 三视图 · Planner · 修习 Runner · 量化与保持 · 制品与分发 | `v0.1.0` | 五动作闭环跑通；三端安装包可安装、可启动、**能加载到内容** |
| **P2** | 笔记与治理 | Note 三层 · 单向导出 · overlay 双平面 | `v0.2.0` | 笔记可写可导出；治理层不侵入事件内核 |
| **P3** | 上架与分发 | 商店审核 · 更新机制 · 分发渠道 | `v1.0.0` | 通过 App Store 审核；分发渠道可用 |
| **P4** | 服务端与跨设备 | 服务端部署 · 跨设备 HLC 合并 · 私有化交付包 | `v1.1.0` | 双端同步一致；私有化试点交付 |

**三条硬约束**：

1. **阶段代号 ≠ 版本号**。阶段用 `P` + 序号（`P1`–`P4`），版本用三段 `vX.Y.Z`。两者不得混写（如「`V0.1` 阶段」既非阶段代号也非合法版号）。
2. **阶段名只说交付了什么**，不写程度词。范围最小、可用、可行这类信息归出口判据列 —— 写进名字会让名字随判据变。
3. **目标版本单调递增**：`0.1.0` → `0.2.0` → `1.0.0` → `1.1.0`，连续无倒挂。

- **闸门**：每批以一道出口闸门收尾（`G1`–`G9`），过不了不进下一批。**闸门的具体断言随该批开工写入对应 PR 描述，本文件只登记闸门与批次的归属，不复制断言内容** —— 复制一份就有两份可改。

### 4.3 分阶段计划 · P2 / P3 / P4

| 阶段 | 批次 | 里程碑 | 关键内容 | 出口判据 | 出处 |
|---|---|---|---|---|---|
| **P2** | `B7` | 笔记与治理 | Note 三层 · 单向导出 · overlay 双平面 | 笔记可写可导出；治理层不进内核 | 明文 |
| **P3** | 未拆批 | 上架与分发 | 商店审核材料 · 更新机制 · 分发渠道 | 过审 + 渠道可用 | 本次新增 |
| **P4** | `B9` | 服务端落位 | 服务端部署形态 · 云 / 私有化 · 跨设备 HLC 合并 | 双端同步一致 | 明文 |

**两处分界判据**：

1. **按「是否纯客户端」切**，不按体量对半。`P2` 全部可离线验收，`P3`/`P4` 的验收才只需关注商店与服务端本身。
2. **跨设备 HLC 合并随服务端**，不提前到 `P2`。合并算法没有第二台设备就写不出可观测断言（`X-05`），提前做只能得到构造出来的证据，风险被暂时掩盖。
3. `P3` 不预先拆批 —— 拆批依赖 `P4` 结束时的真实形态，现在拆只能凭空猜。
4. **私有化交付包在 `P4` 而非 `P3`** —— 它依赖服务端容器，订单不能排在依赖之前。

### 4.4 关键路径

```
α 真实内容包 → 投影帧预算 → 事件内核 → 三视图 → Planner → 修习 Runner → 制品与分发
```

- `P2` / `P3` / `P4` **都不在 `v0.1.0` 的关键路径上**。
- 上架不等服务端：`adr/0002` 明文「服务端不在关键路径」，若上架须等服务端，服务端即成关键路径，与该裁定矛盾。
- `P1` 内 `B8` 排最后但**不是「最后再说」**：所有路径假设都建立在「从仓库根跑」之上，只有打包才会让它们暴露。`project-language` 实际上过这个当（上架包里没有任何语言包）。

## 七、风险

### 7.1 台账

状态列三档：**已发生**（真出过事，写清根因）· **已规避**（曾有可能，已用机制堵住）· **未发生**（仍开着）。

| # | 风险 | 状态 | 根因 / 机制 | 归属 |
|---|---|---|---|---|
| **R-01** | 交付物体系「规范有、入口无」 | **已发生** | 25 种交付物曾被写在 `docs-system.md`（归 S2），但 **S0 出口判据不引用它**；骨架权威处的 `docs/` 只画一行 `README.md`；`project-retrofit.md` 写「缺则**建索引**」（反向措辞）；`check_s0.py` 零检查。**四处同时失效**，任一处在位都能拦住 | 已修（PR `#14`） |
| **R-02** | CI 判据静默放行 | **已发生** | `content-checks` 第四步原判据两端失真：**过宽**（要验 `dist/` 被忽略，却实现成「全仓不得有未跟踪文件」）⇒ 任何无关临时文件都红；**过窄**（`^??` 只匹配未跟踪，`dist/` 若已入库则显示 `M`）⇒ 漏掉最该抓的情况。它红的那一次恰是误报，该抓的一直抓不到 | 已修（PR `#13`） |

| **R-04** | 打包后内容包路径全部失效 | **未发生** | 开发期路径假设建立在「从仓库根跑」之上。装成 exe / ipa 后该路径不存在 ⇒ **安装包能启动但一条内容都没有**。`project-language` 实证过（上架包里无语言包）。本项目选 **exe 同级解析**，但该方案在 App Store 形态下不成立（bundle 只读且签名校验）⇒ `P3` 前必须补回落路径，`B2` 写加载器时就要把「路径探测」与「解析」拆开。**`B2` 第 2 笔已拆**：`PackProbe`（找目录 + 三类失败原因）与 `parsePack`（两段文本 → 实体，零磁盘）分层，候选根是列表 ⇒ 补一条安装形态的路径只加一个候选根，解析层一行不动；`dart:io` 只出现在 `dart_io_pack_fs.dart` 一个文件里 | `B2`（已拆） / `B8`（补候选根） |

| **R-06** | 投影帧预算推翻实现方案 | **已关闭** | 全案唯一可能**改实现路径**（非仅调参）的未知，已前置到 `B2`，输入用 α 真实包图密度。**2026-10-17 结案**：终端四组实测（[`STR`](../04-test/STR-软件测试报告.md) 轮次 `R1`）三档 + 全屏均达 `C-32` 优线，实现路径不必改。但**风险落点变了** —— 原风险盯 CPU 投影（实测 `0.03 ms`，比预算低两个数量级），真实约束是**光栅 × 覆盖面积**：同场景面积 `1.55×` ⇒ 光栅 `2.02×`，基准窗口下已占帧预算 **88%**，4K 按面积推需约 `27 ms`。**处置已定案（`B3` 笔 6）**：走**分辨率自适应** —— 绘制表面按**物理面积**（`w·h·dpr²`）封顶到 `C-33` 再放大贴满窗口；**否掉限窗**（三端窗口能力不一致、且限逻辑尺寸挡不住系统缩放、还把成本问题换成可用性问题），依据见 [`ADR-0002`](../../adr/0002-dev-order-vertical-slice.md) 修订三 | ✅ 已关闭（`ADR-0002` 修订三） |

| **R-12** | 记录类文档被追溯补写 | **已规避** | `DPMR` / `STR` 的价值全在「当时确实如此」，补写即从证据退化为叙述。已立判据：**这份文档是在记录一次已发生的事，还是在描述当前应当如此？** 前者不补 | 已规避 |
| **R-13** | Apple 账号 / 公证证书未就位 | **未发生** | 行政周期不可控，且**不受开发进度影响**。没有账号 `B8` 的 iOS 制品无法签名；没有公证 `dmg` 过不了 Gatekeeper。上架已提前到 `P3`，这条比原先更紧 | `P1` 开工前（见 §4.5） |

### 7.2 从台账里能读出的三件事

1. **四条已发生的文档类风险（R-01 / R-10 / R-11 / R-12）都不是「忘了写」，而是「规则写得看似成立、实际失效」**。R-01 是四处规则同时缺位，R-10 是给降标做了合法性包装，R-11 是判据与产出冲突。这类问题的共同特征是：**文档自洽，行为不自洽**。
2. **两条已发生的 CI 类风险（R-02 / R-03）都是「判据静默通过」而非「判据报错」**。静默通过比误报危险得多 —— 误报会有人去查，通过不会有任何人发现。
3. **两条未发生的风险（`R-04` / `R-13`）都属「现在不办、后面无解」**，其余风险都可随批次收敛。这两条是 §4.5 长周期前置的来源。
4. **`R-06` 是台账里唯一一条「结案但结论不等于『没问题』」的**：帧预算达标，风险落点却从 CPU 移到光栅 × 覆盖面积。原判据（CPU `8 ms`）盯错了地方 —— 实测 CPU 只花 `0.03 ms`；而小窗读数（余量 57%）与基准窗口读数（占预算 88%）指向相反的行动。**性能类读数必须带测量前提**，否则「通过」只是一个尺寸下的巧合。
