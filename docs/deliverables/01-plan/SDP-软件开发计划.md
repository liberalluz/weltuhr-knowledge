## 一、范围

`v0.1.0` 的范围 = **登录之后，一条学习主链的端到端贯通**，五个动作构成闭环：

```
登录 → 加载空间 → 圈定目标 → 建 Plan → 学一项 → 判合格写事件
```

范围裁定与理由见 [`../../adr/0002-dev-order-vertical-slice.md`](../../adr/0002-dev-order-vertical-slice.md) 与 [`../../adr/0004-accounts-as-usage-prerequisite.md`](../../adr/0004-accounts-as-usage-prerequisite.md)（本文件不复制）。`v0.1.0` 之外的条目由 §4.3 承接。

**明确的边界**：**登录是使用前提**（`ACC-001`，由 `ADR-0004` 推翻原「首期不依赖服务端」）—— 但登录一次之后离线完整可用。笔记、治理、**跨设备同步**不在 `v0.1.0` 内。

**三条硬约束**：

1. **阶段代号 ≠ 版本号**。阶段用 `P` + 序号（`P1`–`P4`），版本用三段 `vX.Y.Z`。两者不得混写（如「`V0.1` 阶段」既非阶段代号也非合法版号）。
2. **阶段名只说交付了什么**，不写程度词。范围最小、可用、可行这类信息归出口判据列 —— 写进名字会让名字随判据变。
3. **目标版本单调递增**：`0.1.0` → `0.2.0` → `1.0.0` → `1.1.0`，连续无倒挂。

- **`B12` 的笔序不进本文件**：它拆 `V-1a`–`V-1i` 九笔，其中 `V-1c`（`Z3` 渲染 + 共面轨道）**提前于入口** —— 那时 `Z1` / `Z2` 尚不可点，验收只能靠注入状态；`V-1i`（`Z0` 公转 72 s）可延后至 `B12` 之后单独一笔。笔序表与逐笔闸门断言随 `V-1a` 开工写入 `B12` 首个 PR 描述，与本文件「只登记闸门与批次的归属」同一条理由。
- **`B12` 不改 `B3` 的出口判据**：`G3` 已判条件通过（唯一条件为终端三视图观感），新批次不重新打开它。`B12` 完成后 `G3` 的条件仍然只有一条 —— 观感，而不是「五档都有可点对象」，后者是 `B12` 自己的出口闸门。
- **`userId` 不是 `B10` 的内容**：`ACC-013` 要求 `userId` 在 `v0.1.0` 就进事件信封，而 `B4` 一开工就会写事件 —— 两者在时间上都早于 `B10`。落地时**随 `B4` 第一笔一起做**（补信封字段 + `fold` 按 `userId` 过滤），`B10` 只负责「登录 + 会话 + 两屏 + 首启拦截」。把它塞进 `B10` 就等于让 `B4`～`B6` 期间写下的全部事件需要迁移。
- **出处等级**：「明文」= `adr/0002` 有直接表述；「推定」= 按其批次框架推出，ADR 无逐条对应。推定项在**首次开工时回填为明文**，回填须给出新增依据。

### 4.3 分阶段计划 · P2 / P3 / P4

| 阶段 | 批次 | 里程碑 | 关键内容 | 出口判据 | 出处 |
|---|---|---|---|---|---|
| **P2** | `B7` | 笔记与治理 | Note 三层 · 单向导出 · overlay 双平面 | 笔记可写可导出；治理层不进内核 | 明文 |
| **P2** | `B11` | 跨设备同步 | 增量上行/下行 · 三端点 · 三张表 · 包版本握手 · `identity` 完整分层（验证 / 找回 / 多设备） | 两台设备同账号互见；包版本不一致时拒绝而非丢事件 | 本次新增（`ADR-0004`） |
| **P3** | 未拆批 | 上架与分发 | 商店审核材料 · 更新机制 · 分发渠道 | 过审 + 渠道可用 | 本次新增 |
| **P4** | `B9` | 双向合并与私有化 | 双向合并算法 · 私有化部署形态 · 账号源对接（OIDC / LDAP） | 双端合并结果一致；私有化试点交付 | 明文（表述随 `ADR-0004` 修订） |

**两处分界判据**：

1. **按「是否纯客户端」切**，不按体量对半。`P2` 全部可离线验收，`P3`/`P4` 的验收才只需关注商店与服务端本身。
2. **「搬运」进 `P2`，「合并」留 `P4`**。`ADR-0004` 把增量同步提前到 `P2`（`B11`），但它只搬不判（`X-09`）；**双向合并算法**仍留 `P4` —— 没有第二台设备就写不出可观测断言（`X-05`），提前做只能得到构造出来的证据，风险被暂时掩盖。
3. `P3` 不预先拆批 —— 拆批依赖 `P4` 结束时的真实形态，现在拆只能凭空猜。
4. **私有化交付包在 `P4` 而非 `P3`** —— 它依赖服务端容器，订单不能排在依赖之前。

### 4.4 关键路径

```
账号与登录 → α 真实内容包 → 投影帧预算 → 事件内核 → 三视图 → 三视图逐级下钻 → Planner → 修习 Runner → 制品与分发
```

- **`B12` 排在 `B4` 之前是硬依赖**：`B4` 的三段流程第一步就是「圈定目标」，而圈定动作发生在三视图里。`B3` 收尾时 `Z1` / `Z2` 尚无**可点对象**（`r` 只是扇环分段、没有实体），不先补 `B12`，`B4` 的验收就只能靠构造输入 —— 那等于用假输入证明真流程。
- `P2` / `P3` / `P4` **都不在 `v0.1.0` 的关键路径上**。
- **上架不等同步**：`ADR-0004` 把**账号服务端**前移到 `P1`（否则登录门槛无法成立），但**增量同步仍在 `P2`**。`P3` 上架不需要同步完成 —— `v0.1.0` 交付时账号已可用，同步是下一个版本的能力。
- `P1` 内 `B8` 排最后但**不是「最后再说」**：所有路径假设都建立在「从仓库根跑」之上，只有打包才会让它们暴露。`project-language` 实际上过这个当（上架包里没有任何语言包）。
- **`B10` 排在 `B8` 之前是硬依赖**：制品里必须含登录屏，否则装出来的包一启动就停在「未登录且无法登录」。

### 7.2 从台账里能读出的三件事

1. **四条已发生的文档类风险（R-01 / R-10 / R-11 / R-12）都不是「忘了写」，而是「规则写得看似成立、实际失效」**。R-01 是四处规则同时缺位，R-10 是给降标做了合法性包装，R-11 是判据与产出冲突。这类问题的共同特征是：**文档自洽，行为不自洽**。
2. **两条已发生的 CI 类风险（R-02 / R-03）都是「判据静默通过」而非「判据报错」**。静默通过比误报危险得多 —— 误报会有人去查，通过不会有任何人发现。
3. **`R-04` / `R-13` 仍属「现在不办、后面无解」**，是 §4.5 长周期前置的来源。新增的 `R-15`–`R-18` 属**同族** —— 它们的共同特征不是「难」，而是**违反了不会有任何东西变红**（`R-08` 的判据）：服务端没登录拦不住也不会报错、包版本不一致时丢一条事件没人知道、两个账号的进度混在一起只表现为一个「莫名其妙」的数字。**这类风险只能靠显式裁定堵，不能靠测试发现**，所以它们被写成了 `ACC` / `SYNC` 里的裁定，而不是留待实现时注意。
4. **`R-06` 是台账里唯一一条「结案但结论不等于『没问题』」的**：帧预算达标，风险落点却从 CPU 移到光栅 × 覆盖面积。原判据（CPU `8 ms`）盯错了地方 —— 实测 CPU 只花 `0.03 ms`；而小窗读数（余量 57%）与基准窗口读数（占预算 88%）指向相反的行动。**性能类读数必须带测量前提**，否则「通过」只是一个尺寸下的巧合。
