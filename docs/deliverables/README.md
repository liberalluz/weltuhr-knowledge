## 二、与设计基线的关系（引用不复制）

交付物**引用不复制**设计规格。具体做法：

- `SRS` 的每条需求挂 `SPEC-<域>-<NNN>` 编号，正文只写需求陈述与验收指向，不复制判据理由；
- `SDD` 的分章与 `specs/` 的主题文档对齐（当前已映射八份，`ACC` / `SYNC` 待补），实现细节回指；
- `STP` 的测试用例直接以各份规格末的**验收表**（裁定号 / 可观测断言 / 测试向量 / 预期）作为种子。

**这样做的理由**：设计基线会随讨论演进，交付物按版号冻结。若复制，「设计改了交付物没改」必然发生。

## 三、随 PR 更新（硬纪律）

功能 PR 自带文档增量，**不另开文档 PR 补**。默认单据：

| 本次 PR 改了什么 | 同 PR 必须更新 |
|---|---|
| **任何功能 PR** | `DPMR`（本期做了什么、哪条没通）· `STR`（本轮实际跑通什么） |
| 测试 | + `STP` · `STD` |
| 架构 / 分层 | + `SDD` |
| 接口 / 契约 | + `IRS` · `IDD` |
| 库表 / 迁移 | + `DBDD` · `DRD` |
| 排期 / 里程碑 / 风险 | + `SDP`（§4 · §七） |

**四条硬判据**：

1. **默认单据两项（`DPMR` + `STR`）不得同时为空** —— 若确实无需更新，PR 正文须写明理由，不得静默跳过。
2. **PR 正文必须列出「交付物增量」**，逐份写文件名（模板见 [`.github/PULL_REQUEST_TEMPLATE.md`](../../.github/PULL_REQUEST_TEMPLATE.md)）。
3. **事后补写须标「追溯补录 + 日期」**，不得伪装成当时所写 —— 追溯的可信度来自如实标注，不来自内容完整。
4. **记录类文档不得追溯补录**（`DPMR` · `STR`）—— 它们的价值全在「当时确实如此」，补写即从证据退化为叙述；承诺类（`SDP` · `SDD` · `STP` · `SCMP`）描述「当前应当如此」，可补。
