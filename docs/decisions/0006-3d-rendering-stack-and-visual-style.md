# ADR-0006 · 3D 渲染栈与视觉风格

- **状态**：已接受（2026-10-30 修订一至四、2026-10-31 修订五至十二、2026-11-01 修订十三，见文末）
- **日期**：2026-10-20 · 修订 2026-10-30
- **决策人**：liberal
- **覆盖范围**：[`ADR-0005`](0005-three-axis-tree-replaces-six-axis.md)「未在本 ADR 决定」的第一项（3D 渲染技术栈）· [`ADR-0003`](0003-view-radial-axis-and-channel-thresholds.md) 的通道判据（**前提已由 `ADR-0005` 取代，本 ADR 只接其视觉资产部分**）· `SPEC-VIEW-*` 的渲染前提

## 背景

视觉侧的四条已定，本 ADR 不重开：

| 项 | 结论 | 出处 |
|---|---|---|
| 背景 | 烘焙天球 —— Yale BSC5 公有领域 9,110 颗 + 程序化补到 2 万 | 需求侧 |
| 前景 | A 案外观（自绘）+ B 案标注层（Flutter Widget 叠加） | 需求侧 |
| 色彩 | **色温让给轴** —— 学科青 / 专业琥珀 / 角色洋红紫 | 需求侧 |
| 布局 | 同心球壳，半径按对数等比 | 需求侧 |

缺的是**怎么在 Flutter 上把它画出来**。四条硬约束：

1. **2 万颗星不能用 `drawPoints`** —— 性能闸门已禁 >10,000 点，且 `drawRawPoints` 在 2 万量级不可行（旧结论）。背景必须是一张**烘焙贴图**，运行时零顶点。
2. **`bloom` 是「接近真实宇宙」的硬需求** —— 星点光晕是这项观感最直观的一项。而 bloom 需要**多 pass**（亮部提取 → 多级模糊 → 合成）。
3. **三端**：Windows / macOS / iOS，一套代码。
4. **`core/` 不得 import Flutter** —— 渲染实现只能落在 `features/universe/`。

第 2 条是选型的实际决定项：**Flutter 的 `FragmentProgram` 是单 pass 的**，拿不到离屏目标做二次处理，因此纯 shader 方案先天做不出 bloom。

## 决策

### 1. 渲染栈 = `flutter_scene`

| 项 | 取值 |
|---|---|
| 包 | `flutter_scene` |
| 版本 | `0.24.3` —— **钉死到补丁位**，不用 `^` |
| 生效范围 | `app/lib/features/universe/presentation/` —— `core/` 与 `application/` 不得 import |
| 平台 | Android / iOS / Linux / macOS / Web / Windows 全覆盖；本项目只用三端 |

**版本钉死，不用 `^`（本 ADR 修订一）**：仓规要求版本钉死（`app/pubspec.yaml` 顶部同一口径，全部依赖写精确版本）。原决定的 `^0.23.0` 在 pub 语义下等价 `>=0.23.0 <0.24.0`，锁 minor、允许补丁漂移；而该包 0.14 与 0.22 均有 `BREAKING`，minor 恰恰是会出大变化的那一位。钉到补丁位同时满足仓规与原意，更严一档。

**为什么是 0.24.3 而不是 0.23**：本 ADR 原文写「0.24 须手动升并重跑 spike」，即允许升、只要求重验。spike 一次未跑时，此刻升 0.24 是零成本；若先用 0.23 验完再升，三端采帧要重跑一次。本次就是首验。

选它的唯一实质理由：**`Scene.skybox` + `EnvironmentSkySource` 与 `Scene.postProcess` 同时提供**，前者吃 equirect 全景图，后者含 bloom / 色彩分级 / 暗角 / 景深。自研要分别实现这两块，其中 bloom 的自研成本不低于整个天球采样。

### 2. 使用面限定：只用 skybox 与后处理

`flutter_scene` 是完整 3D 引擎（PBR、物理、骨骼动画、粒子、glTF、GI）。**本项目只用其中三项**：

- `Scene.skybox` + `EnvironmentSkySource` —— 承载烘焙天球
- 相机（球心视角，只旋转不平移）
- `Scene.postProcess` —— bloom（必需）· 色彩分级（`色温让给轴` 的全局压调）· 暗角（可选）

**明确不用**：物理后端 · 骨骼动画 · 粒子系统 · glTF 资产 · 全局光照 · 阴影。理由：这些每一样都会把依赖面与升级风险放大，而对「从球心看星空」零收益。行星与恒星都**不是 3D 模型**，是贴图上的点 + Flutter Widget 标注。

### 3. spike 闸门：`B17b` 开工前必须先跑

Impeller 在三端的启用状态、`flutter_scene` 的实际帧时间，**只能实跑确认**。沙箱不能 `build`/`run`，故本 ADR 不预置「已验证」结论。

**spike 内容**（原定三端各一次；Windows 已采，见第五节）：最小场景 = 天球贴图 + 1,200 个 billboard 点 + bloom 开启。

| 判据 | 阈值 |
|---|---|
| 帧率 | P50 ≥ 30 fps，P95 帧时间 ≤ 50 ms（`B17b` 的 60 fps 目标不在 spike 判据内 —— spike 验「能不能跑」，不验「跑得多好」） |
| 白屏 / 崩溃 | 0 次 |
| 渲染路径 | 无 `PlatformView`、无 fork、无**自写**原生渲染代码 |
| 三端一致 | Windows 必过；macOS / iOS 暂缓（2026-10-31 裁定，见修订五）。恢复验时按同表判，任一端不过即判该端 spike 失败 |

**「无原生平台代码」的边界（本 ADR 修订二）**：这条禁的是**自己写渲染**的原生实现（`ADR-0006` 被否方案④那种 FFI / Metal / D3D12），不是禁「开一个引擎开关」。`flutter_scene` 0.24 要求显式开启 Flutter GPU，而 Windows 侧的开关只能写在 `windows/runner/main.cpp` 里 —— 那是一行 `project.set_enable_flutter_gpu(true)`，不含任何渲染逻辑。若按字面把这一行也算违规，三端就只剩「每次跑带命令行参数」一条路，而 release 构建不认那个参数 —— 判据会把可行的做法判死。故口径收窄为「自写」，一行配置开关不算。

**失败处置**：回落 `FragmentProgram`（每像素反投影）+ 预渲染光晕 sprite，并把本 ADR 标为**已取代**、新立 ADR 记录取舍。回落后接受「无真 bloom」这一观感损失，须在 ADR 中显式写明。

### 4. 天球贴图是构建产物，不入库

一张 4096×2048 的 equirect 全景图约 8–15 MB（PNG）/ 2–4 MB（KTX2），而 `ADR-0005` 决策 2 给骨架包的预算是「数百 KB」—— **贴图不能进骨架包**。

| 项 | 结论 |
|---|---|
| 生成 | **运行期**由星表画出（2026-10-31 修订六把「构建期烘焙、脚本置于 `infra/`」改为运行期；修订七把星源由 `V/50` 换成 Hipparcos） |
| 入库 | **否** —— 仓规「构建产物不入库」直接适用（同 `content/` 的 `dist/`） |
| 分发 | 随制品打包，不进骨架包，不参与包版本握手 |
| 分级 | 4096×2048（默认）/ 8192×4096（FOV 收窄时）/ 16384×8192（极限，仅桌面） |
| 格式 | KTX2（Basis 压缩）优先 —— `flutter_scene` 原生支持，且体积是 PNG 的 1/3 |

这条同时解决一个口径冲突：`ADR-0005` 的「骨架包数百 KB」与「2 万颗星」并不矛盾 —— **星星在贴图里，不在包里**。

⚠️ **修订六改了「生成」那一行，理由是实现路径变了**：`EnvironmentMap.fromUIImages` 收的是运行期 `ui.Image`，不需要任何文件。于是「不入库」不再靠纪律守，而是**没有可入库的东西** —— 连临时文件都不落地。代价是启动时多一步绘制（实测 < 200 ms），收益是构建不必联网、CI 不因外网抖动变红。原文的 KTX2 / 分级两行仍然有效（真需要预烘时按它走），只是当前路径不走它。

**星表原文入库**（当前为 `content/stars/source/heasarc_hipparcos.tdat.gz`，14.8 MB gz；段 2 的 `bsc5.dat.gz` 已随修订七删除）：源数据入库、产物不入库，与 `content/skeleton/source/` 存教育部 PDF 原件同一口径。

### 5. 视觉实现口径

| 维度 | 实现 | 判据 |
|---|---|---|
| 天球 | 贴图按 FOV 选级，随相机姿态采样 | 无接缝、无极区畸变 |
| 星点光晕 | `postProcess` 的 bloom，阈值与强度入常量 | 亮星有光晕、暗星不糊 |
| 轴色 | 前景点按 `axis` 着色（青 / 琥珀 / 洋红紫） | 三个轴的恒星在同一屏内可辨 |
| 亮度 | 按掌握度映射，单调不减 | 已学项比未学项亮 |
| 标注 | Flutter Widget 叠加，≤60 条，`Paragraph` LRU 200 | 超 60 走聚合，不缩字号 |
| LOD | 同屏语义节点 >1,200 转聚合 | 帧率不因节点数抖动 |
| 过渡 | 虫洞过渡为相机弧线插值，时长入常量 | 中途不出现空白帧 |

### 6. Flutter GPU 的启用方式（本 ADR 修订三）

`flutter_scene` 建在 Flutter GPU 之上，而 Flutter GPU **默认关闭**，每端须开一次。开发期可以靠命令行的 `--enable-flutter-gpu` 临时打开，但 **release 构建不认这个参数** —— 所以三端写死在各自的平台文件里，而不是靠命令行。

| 平台 | 位置 | 写法 |
|---|---|---|
| Windows | `app/windows/runner/main.cpp` | `project.set_enable_flutter_gpu(true);`（需引擎头文件有此方法，已核对本机 SDK 存在） |
| macOS | `app/macos/Runner/Info.plist` | `<key>FLTEnableFlutterGPU</key><true/>` |
| iOS | `app/ios/Runner/Info.plist` | 同上 |

**两条前置**：Flutter 须 3.47 以上（本机 3.47.7）；**Windows / Linux 要出 release 包须 3.47.1 以上**，3.47.0 会把引擎的环境开关编掉。

**回滚条件**：这三处开关随 `flutter_scene` 存在。若 spike 失败、本 ADR 转为「已取代」并回落到 `FragmentProgram`，三处必须同时删掉 —— 否则程序仍以 Flutter GPU 后端启动，而没有任何代码用它，等于永久背着一个与功能无关的实验后端。三处均已留注释指明这一点。

## 被否方案

**① `FragmentProgram` 每像素反投影采样。**
天球采样质量最高（无顶点、无接缝、无极区畸变），投影数学还可用 CPU 参考实现单测。**否因是单 pass**：拿不到离屏目标，bloom 只能做单次径向近似的假泛光，拖影明显。若 spike 失败，本方案转为回落目标。

**② `flutter_gpu` 自写渲染器。**
效果上限与 `flutter_scene` 持平，且完全按需裁剪。但 bloom、LOD、tone mapping、纹理 mip 全要自建，工作量等于重造前者；而 `flutter_gpu` 本身 API 仍在演进。**为省一个 0.x 依赖而自建一套引擎，是把依赖风险换成工期风险**。

**③ `drawVertices` 球面网格 + `Canvas` 纹理映射。**
纯 Canvas、零依赖、投影可完整单测，对测试最友好。但球面网格在极点必然挤压变形，接缝处采样会出现细线；且同样无多 pass。天球全景里这两项都是硬伤，观感离目标最远。

**④ 平台原生（macOS Metal / Windows D3D12 / iOS Metal）经 FFI 或 `PlatformView`。**
性能最好，但三端三套实现，且 `PlatformView` 会失去与 Flutter 的合成能力 —— 标注层要浮在 3D 之上，这正是最不能丢的能力。

**⑤ 用 `flutter_scene` 的完整能力（物理 / 粒子 / glTF）。**
见决策 2。多用的每一项都是独立的升级与回归面，而本需求不产生 3D 模型资产。

### 五、spike 实测状态（本 ADR 修订四、修订五）

**Windows 已实测通过**（2026-10-31）。macOS / iOS 尚未实测，按 2026-10-31 裁定暂缓（见修订五）。

| 配置（逻辑 → 物理像素） | 像素量 | 构建 | P50 | P95 | 结论 |
|---|---|---|---|---|---|
| `1280×720` → `1600×900`（125% 缩放） | 144 万 | debug | 3.9 ms | 5.0 ms | 过闸 |
| `1536×960` → `1920×1200`（满屏，125% 缩放） | 230 万 | debug | 4.0 ms | 5.9 ms | 过闸 |

**引用这三组数时，三条口径不得省略**：

- **debug 构建**：`flutter run` 未带 `--profile` / `--release`，含 JIT 与断言开销。release 只会更快，故这组数**不能反推** release 性能。
- **60 Hz 屏幕**：面板上的「249.3 fps / 259.1 fps」是 `FrameTiming.totalSpan` 的倒数，**不等于显示帧率** —— 60 Hz 屏每秒最多 60 帧。判据按帧时间算（`p50Ms <= 1000/30`），不看这个 fps 数。
- **125% 系统缩放**：`Win32Window::Size` 收的是**逻辑像素**，物理 = 逻辑 × 1.25（`windows/runner/win32_window.cpp` 的 `Scale(size.width, scale_factor)`）。写窗口尺寸必须换算，否则窗口溢出屏幕、读数随之失真。

**像素翻 1.6 倍、P50 只涨 0.1 ms** —— 本栈在 spike 负载下**不是填充率瓶颈**：bloom 的多段全屏后处理、天球贴图采样、230 万像素光栅化，边际成本接近零。段 2 可直接用这条结论：加大贴图与后处理几乎不花帧时间，真正的成本在**几何实例数** —— 1,200 个 billboard 是当前唯一的几何负载。

`spike` 的形态**当时**定为独立入口：`app/lib/spike_main.dart`，用 `flutter run -t lib/spike_main.dart` 启动，不经过主 app 的任何路由 —— 主界面刚通过 `B4` 验收，不为一次实验增加分支。读数面板在左上角，**至少采 8 秒**后给出 P50 / P95 与是否过闸（修订六改，原为「采满 300 帧」）。

⚠️ **这一条已被修订十三部分推翻**：`B17b` 笔 2 把渲染整包搬进 `features/universe/presentation/`，并在容器树标题栏加了「宇宙视图」入口 —— 产品路径上确实多了一个分支，理由是它从「一次实验」变成了「产品功能」。`spike_main.dart` 保留为调试入口，采样面板只在那里显示（`SpikeSceneView.showReadout` 默认关）。

**采样时长与机器性能绑定的缺陷已在段 2 修掉**：原 `kSampleFrames = 300` 的注释按「30 fps 下 10 秒」估算，而在 249 fps 的机器上 300 帧只有约 1.2 秒；且采样在启动后立刻开始、采满即定格，**窗口来不及放大**。判据改为按**时长**（`kSampleSeconds = 8.0`），面板同步显示「已采 X / 8.0 秒」。判据的形态从「帧数」改成「时长」不是放宽：分位数需要的是样本量，而样本量在快机器上自然更多 —— 慢机器也不会因为帧数不够而提前结束。

**其中一处读数口径改了实现**：判「P50 ≥ 30 fps」时直接比帧时间（`p50Ms <= 1000/30`），不先换算成 fps 再比 30。两者数学等价，但 `1000 / (1000 / 30)` 在浮点下会落在 `29.999999999999996`，让恰好压线的读数翻成不通过。这不是放宽判据，是去掉换算引入的假阴性。

## 段 2 落地：星空外观与球壳（本 ADR 修订六）

笔 1 的星空是 `Random(20261030)` 撒出来的占位：位置随机、亮度随机、银河随手画一条斜带。段 2 把它换成真的：

| 项 | 实现 | 落地 |
|---|---|---|
| 星位 / 亮度 / 颜色 | `V/50` Bright Star Catalogue 的 J2000 赤经赤纬、视星等、`B−V` | `content/stars/source/bsc5.dat.gz` + `app/lib/features/universe/presentation/star_catalog.dart` |
| 银河 | 银道面大圆，由 ICRS→Galactic 旋转矩阵反解 | `app/lib/features/universe/presentation/sky_image.dart` |
| 星点形状 | 运行期画的径向渐变光斑，加性混合 | `app/lib/features/universe/presentation/star_sprite.dart` |
| 同心球壳 | 5 层，半径对数等比（8 → 约 55，最外层仍在天球内） | `app/lib/features/universe/presentation/sphere_shells.dart`（经纬网格已随修订十删除，只留结构定义） |

四条取值与理由：

1. **暗星烘进贴图、亮星做成 billboard**，分界在 1,200 颗（`kSpikeBillboardCount`）。依据是第五节的实测 —— 填充率不是瓶颈，几何实例数才是。9,096 颗星里最亮的 1,200 颗占几何，其余 7,896 颗留在贴图。
2. **球壳取 5 层，按三轴最深的那条（角色 5 层）**，学科与专业只用前 4 层、最外层留空。不为视觉对称凑层 —— 深度是编目的函数（`MEMORY-rules` §三 同学科轴那条）。
3. **星表原文入库、贴图不入库**。星表是源数据（590 KB gz），贴图是产物；因为走 `EnvironmentMap.fromUIImages`，产物连临时文件都不落地。
4. **球壳是参考线，透明度压到 0.10**。相机在球心时球壳本身看不见，画经纬网格只是让「几层、比例对不对」在没有节点时就可验。

   ⚠️ **本条已被修订十推翻**：球心视角下五层同经纬度点投影后完全重合，「几层」看不出来；有效透明度也不是 0.10 而是叠了五次约 0.41。网格已整层删除，详见「球壳网格移除」一节。

⚠️ **仍未验的一项**：macOS / iOS 两端（按 2026-10-31 裁定暂缓）。段 2 的改动全在 Dart 侧与数据侧，没有新增原生配置，但**未在另两端实跑过**。

## 段 3 落地：星空收口（本 ADR 修订七）

段 2 把星位换成了真的，但只到 9,096 颗、7.96 等 —— 亮星表就这么多，画面是疏星点点。
段 3 换成 Hipparcos 全量，并把「可旋转可缩放」与「无极区畸变」两条判据落下来。

| 项 | 段 2 | 段 3 |
|---|---|---|
| 星源 | `V/50` Bright Star Catalogue（公有领域） | Hipparcos 主表（HEASARC 转制版，需署名） |
| 颗数 | 9,096（billboard 1,200 + 贴图 7,896） | **118,217**（billboard 1,200 + 贴图 117,017） |
| 极限星等 | 7.96 | 9.5 |
| 相机 | 按时间自动绕行 | **手势旋转 + 滚轮缩放**，拖动后停止自转 |
| 极区 | 不处理（横向拉伸） | **绘制期预补偿**：横向画宽 `1/cos φ` 倍 |
| 银河 | 等亮的一条带，边界像刀切 | 按银纬 24 层羽化，边缘平滑到 0（2026-10-31 修订八改为单路径羽化，见下） |

四条取值与理由：

1. **全用 118,217 颗，不再「补到 2 万」**。决策表「背景」那行写的 2 万，是只有亮星表时的目标数 —— 其中约 1.1 万非要编造位置。换成 Hipparcos 后真星就有 11.8 万颗，一颗不用编；而 4096×2048 的贴图上 11.8 万颗的平均间距是 8.4 px，屏幕放大 2.4 倍后约 20 px、暗星点 2.4 px —— 分得开、不糊。**「2 万」这个数由实测取代，不是被放宽**。
2. **换源而不是叠加源**。Hipparcos 与 BSC5 高度重叠（BSC5 的星几乎都在 Hipparcos 里），两张表叠起来要自己去重；而 `V/50` 在 6.5 等以下本就不全，留它没有增量。旧表随同一笔删除。
3. **极区在绘制期补偿，不换贴图形态**。`EnvironmentMap` 内部本来就是 cubemap，但可见天空**直接采样全分辨率 equirect 源图**（为了 sharp），所以畸变在**源图**里 —— 换 cubemap 救不了。正确解法是画的时候就按 `1/cos φ` 把星点横向拉宽，投影回球面正好是正圆。
4. **补偿只做到 \|φ\| = 80°，再往上退回不补偿**。倍数在那里发散（85° 是 11.5 倍、89° 是 57 倍），贴图横向像素也不够；硬补会把星点抹成横条。退回正圆后球面上是「更小更暗的点」，比横条自然。

### 已知边界（本段不解决，登记在此）

- **极点 ±10° 的星点形状不准**：不补偿 ⇒ 球面上是竖向压扁的椭圆。那片天区都是 8 等以上的单像素暗星，肉眼分辨不出形状；北极星（1.97 等）在 billboard 里，不受此影响。
- **接缝处边缘星点被切一半**：等距柱状图左右两边是同一条经线，落在图边缘的星点会被画布裁掉一半，转到接缝时能看到「半颗星」。修法是在另一侧补画一份，本段未做。
- **贴图层是单色**：117,017 颗暗星统一一个偏冷的白，没有按 `B−V` 上色。色温留给 billboard（1,200 颗亮星）—— 暗星在屏幕上只有 2–3 像素，上色也看不出来。**轴色（学科青 / 专业琥珀 / 角色洋红紫）只给节点，背景星保持真实色温**，两者不抢同一层。

### 未验

段 3 的实机画面与帧率**已采集**（2026-10-31，Windows，1920×1200，只 Windows）：三处观感都过 —— 星点 2–3 px 正圆、极点汇聚处无横条、银河外缘暗纹随修订八消失。「抬头找到北斗」当时仍未过：星点之间没有连线，静帧里指认不出那七颗（→ 段 4 修）。

帧率读数四次（30 秒窗口、fov 70°、自转中）：P95 **20.5 / 8.1 / 11.5 / 9.0 ms**，P50 4.7 / 5.7 / 5.3 / 5.5。段 2 那条 27.2 ms 是**首帧上传的暂态**，不是稳态 —— 稳态 P95 落在 8–11.5 ms，距 60 Hz 的 16.67 ms 最差也有 1.45 倍余量；20.5 那一轮是孤例，按「事先定好：连测三次回到 8–11.5 即判瞬态」处置，不改代码。⚠️ 面板的闸门判据是 `P50 ≥ 30 fps`，P95 20.5 照样判「通过」—— **「闸门通过」不等于「60 Hz 稳」**，两者别混读。

## 段 3 修正：银河羽化改单路径（本 ADR 修订八）

段 3 的银河按银纬切 **24 层**，每层一个闭合多边形、各给一个不透明度。层与层是**各自独立的填充**：公共边被抗锯齿各算一次，覆盖率拿不满，于是每条缝都与两侧不同 —— 24 层就是 23 条缝，间距正好一层宽（0.75°）。

**这不是推测，是测出来的**：沿银道面法向采样，旧实现相邻采样点跳 **16/255**（银道面附近最大，向带外递减）。`TC-SPIKE-028` 在旧实现下直接红。

改为**一条路径、一次填充**，边缘靠 `MaskFilter.blur` 摊开：形体半宽取亮带半宽的一半、σ 再取一半，两者叠加后不透明度在半宽处收敛到 `erfc(2) / 2 ≈ 0.002`（不到 1/255），中心仍是满值。

| 项 | 段 3 | 修订八 |
|---|---|---|
| 画法 | 24 层多边形逐层填 | 1 条路径 + 模糊，主带与亮核各一次 |
| 层界痕迹 | 每 0.75° 一处，实测跳 16/255 | 无内部边界 |
| 衰减曲线 | `(1 − t)²` | 模糊给出的 erfc，中心满值、半宽处 ≈ 0 |
| 判据 | 纯函数单调（`milkyWayAlphaAt`） | **渲图采样**：相邻像素差 ≤ 3/255，且单调不增 |

代价与取舍：曲线形状从 `(1 − t)²` 换成 erfc，两者在半宽处的斜率不同，但都在低不透明度区，肉眼不可辨；换来的是没有内部接缝。`milkyWayAlphaAt` 随实现一起删除 —— 留着它就是只为测试存在的死函数。判据同时从「公式单调」改成「读画出来的像素」，后者更严：公式连续不代表填充没缝，段 3 的缝恰恰是公式测不到的。

⚠️ **未证的一项**：2026-10-31 实机截图里、银河带**外缘**那排斜向暗纹，是否就是这些层缝，本笔**没有证明**。层缝在银道面附近最强、向带外递减，与「暗纹出现在外缘」并不完全吻合 —— 修掉层缝可能只是必要条件。实机同角度对比是唯一判据，在看到对比图之前不得写成「已修复」。

## 段 4 落地：星座连线（本 ADR 修订九）

「抬头能找到北斗」这条验收此前**没法验**：118,217 颗星点之间没有任何连线，静帧里指认不出哪七颗是北斗。本节加一层屏幕层 overlay，画北斗、猎户、仙后三条连线与星座名。

| 项 | 取值 | 理由 |
|---|---|---|
| 画在哪一层 | **屏幕层 `CustomPainter`** | 天球贴图启动时画一次，改不了；fov 淡出要每帧按相机姿态重画 |
| 星位来源 | Hipparcos 的 HIP 号，19 颗逐颗反查确认 | 连线关系是自定的，星位一个不编 |
| 广角 | fov 60°–80° 线性淡出到 0 | 广角下满屏是线，会把星空本身盖掉 |
| 接缝 | 两端赤经差 > 180° 整段跳过，不补画 | 补画要在对侧再算一次坐标；跨缝的星座在球面上本来就被切开，硬连是一条假线 |
| 名字 | 只标星座名，fov ≤ 60° 才显示 | 仙后五颗的中文星名（王良几）各资料对应不一致，写错不如不写 |

**投影口径三处必须与引擎一致**，错一处线就不落在星上：星表轴到场景轴用 `(x, z, y)`（与 billboard 同一映射）；右轴取 `up × forward`、上轴取 `forward × right`（`flutter_scene-0.24.3/lib/src/camera.dart:472` 的 `_matrix4LookAt`）；归一化用 `tan(fovY/2)` 与 `tan(fovY/2) · aspect`（同文件 `_matrix4Perspective`）。

代价：每帧多画 19 条线段与最多 3 个 `TextPainter`，相对 118,217 颗星的开销可忽略。真正的代价在**对齐是隐式的** —— 线是 2D 画的、星是 3D 画的，两者只靠一套从源码读出来的坐标约定对齐，没有共享几何可供断言。所以左右手性这类错，测试测不出来，只有实机能看出来。

### 已知边界（本段不解决，登记在此）

- **只有三条**：北斗、猎户、仙后，其余 85 条星座无连线。
- **广角端完全不画**：fov > 80° 时一条线也没有，北斗在 100° 视场下看不见。
- **线宽与字号固定**：1 px 线不随星等变化，12 px 名字在 fov 20° 时偏大。

### 实机核对（2026-10-31 补，本 ADR 修订十一）

三条形状与「线是否落在星上」**已采集**（Windows 1920×1109，fov 50°）：

| 星座 | 结论 | 依据 |
|---|---|---|
| 猎户 | 可辨 | 两肩横线两端压在参宿四（橙红）与参宿五上；两条斜线交叉收腰；腰带三点共线（三点赤纬 −0.30 / −1.20 / −1.94，居中那颗偏离两端连线 0.1°，本来就该是直线）；两条长腿落到参宿六与参宿七 |
| 北斗 | 可辨 | 斗勺四颗围成闭合四边形，斗柄三颗从勺底向左延伸；七颗不多不少，每段端点都有星 |
| 仙后 | 可辨，但「W」是歪的 | 五颗赤纬 ε 63.67 / γ 60.72 / δ 60.24 / β 59.15 / α 56.54 ⇒ 两个谷一深一浅（α 低 4°，δ 只低 0.5°），所以呈压扁的锯齿而非对称 W。这是真实形态，不是连错 |

**投影手性也一并核过**：连线端点与星点重合，没有整体镜像。这一项只能靠实机 —— 镜像之后照样是一条看着像北斗的线，只是与星点整体对不上。

帧率改采 30 秒窗口连测三次（同机、fov 50°、自转中）：P95 **8.3 / 7.2 / 6.9 ms**，P50 4.9 / 4.7 / 4.5 ms，样本 2259 / 2386 / 2418。三次都低于 60 Hz 的 16.67 ms，最差一轮仍有 2 倍余量；也优于段 3 的 8.1 / 11.5 / 20.5 / 9.0 —— 每帧重画 19 条线段与最多 3 个 `TextPainter` 的开销落在噪声以内。

**仍未解决**：星座名压在连线中央（标签取顶点平均位置），辨认时线从字上穿过。产品化时把标签移到图形外侧。

## 球壳网格移除（本 ADR 修订十）

段 2 给每层球面画了 12 条经线 + 5 条纬线，目的是「一眼数出几层、半径比例对不对」（`sphere_shells.dart`）。**这个目的从来没达到**：

相机固定在球心，五层球面上的同经纬度点**投影后完全重合** —— 屏幕上只有一套线，实际是五套叠在一起。后果两个：

1. **亮度叠五倍**。每层 `alpha = 0.10`，五次叠加约 0.41，比星座连线的满值（82/255 ≈ 0.32）还显著。
2. **数不出层数**。「几层」在球心视角下没有环可数；段 3 当时读的是面板上那行「5 层球壳」，不是画面。

fov 拉到 94°、视角靠近球壳极点时最难看：12 条经线在一个点汇聚，整屏像一张蛛网，正好盖在星座上。故整层移除。

**保留的**：五层半径（`kInnermostShellRadius` 8.0 × `kShellRadiusRatio` 1.62）、层数（`kShellCount` 5）、三轴深度（`kAxisDepth` 4 / 4 / 5）三组结构定义 —— 节点落地时要按它们算半径（⚠️ 前三个名字已在修订十三收编进 `C-124`–`C-126`，此处保留当次原文）。`TC-SPIKE-017`（半径等比）与 `TC-SPIKE-020`（三轴深度）仍在守这两条。删掉的只是绘制，以及测绘制的 `TC-SPIKE-018` / `019`（41 → 39 条）。这两条测试编号**从未登记进 STD 台账**（`std.md` 查无此编号，spike 用例只活在测试文件里），所以删用例即为完整处置。

代价说清楚：**「五层结构成立」此后在画面上不可见**，只能等节点落地后看节点的半径落点。之前「可见」是假象，不算证据。

## B17b 笔 1：节点落位（本 ADR 修订十二）

段 1–4 只把**背景**做真了。节点一直没上过球 —— 而「节点在哪」这件事本 ADR 只定了一半：决策 5 的「同心球壳，半径按对数等比」给了**半径**，**方位角从来没有定过**。3,375 个节点里哪一颗在哪个方向，此前没有任何规则。

### 规则

| 项 | 取值 | 落点 |
|---|---|---|
| 半径 | 槽位在该轴上的层序 → `C-124 × C-125^idx` | `core/universe/placement.dart` |
| 子级方位 | 同父的子按官方码排序后落 `C-127 × C-128` = 120 格 | 同上 |
| 来路 | 当前路径各级沿顶部走廊逐级后移 | 同上 |

四条取值与理由：

1. **层序取槽位序，不读 `kAxisDepth`**。那张表记的是「用得上几层」，与本处「第几个槽位」不是同一个量：`discipline` 有三个槽位而表里写 4，直接拿来当索引会把学科轴推到第 4 层、与角色轴的最高层撞在一起。槽位序直接由 `legalSkeletonSlots` 的合法组合给出，是唯一的。
2. **方位由父内索引定，位置可由 `path` 复算**。这是 `SPEC-TREE-007` 的要求 —— 宇宙读树的同一份路径来源，不各算一套。代价是**兄弟增删会让同父其余节点挪位**（骨架随教育部目录升版时会发生）；接受这个代价，因为换成「按码哈希定格」虽然不挪位，却会让同一支的子散落到互不相邻的格子里，那正是聚簇要避免的。
3. **子级占 120 格而非 144**。列 × 行必须 ≥ 骨架最大同父子数（实测 **105**，出现在专业轴某个星系下）。取 12 列让方位角最小间隔 30°；行取 10 而非 12，是因为球面顶部要留来路走廊 —— 球心视角下**半径不改变屏幕位置、只改变遮挡**，祖先与某个子占同一格就是叠成一个点。
4. **子级仰角只铺 −60°..+60°**。极点附近方位角失去意义，铺满到 ±90° 等于把若干节点压成同一点。

### 已知边界（本笔不解决，登记在此）

- **只算一屏**：入参是「一条路径 + 它末位的直接子级」，不给整棵树算绝对坐标。原因是全树绝对坐标必然重叠 —— 不同父的子在同一层球壳上会抢同一批格子，除非真做球面递归细分，而那样深层格会小到失去意义。
- **深层不下钻**：`layoutUniverse` 不返回孙级；下钻是换一次入参，不是同一个坐标系的连续缩放。
- ✅ **同名半径常量已收编**（修订十三）：笔 1 时 `spike/` 里另有一套 `kInnermostShellRadius` 等，与 `C-124`–`C-126` 同值并存；笔 2 已删旧的那套，全仓只剩常量表一份，半径计算走 `shellRadiusOf()`。
- **坐标没有渲染过**：本笔只产出数值与用例，一个点都没画。方位好不好看、120 格够不够疏，要等笔 3 上球才看得见。

## B17b 笔 2：收编与入口（本 ADR 修订十三）

笔 1 之后，渲染代码仍在 `app/lib/spike/`，而本 ADR 的生效范围写的是 `features/universe/presentation/` —— 那份代码是产品的，不该住在实验目录。这一笔把它搬进去，并挂上入口。

**收编**：七个源文件与六组测试整体 `git mv`（同目录内互相 import 保持相对路径，只有跨目录的引用要改）：

| 原 | 现 |
|---|---|
| `app/lib/spike/*.dart`（7 个） | `app/lib/features/universe/presentation/` |
| `app/test/spike/*.dart`（6 个） | `app/test/features/universe/` |
| `app/lib/spike_main.dart` | 保留（调试入口，改 import） |

**入口挂在容器树标题栏**，不是包详情页。依据是 `SPEC-TREE-007`：宇宙视图读树的**同一份当前地址** —— 在树里看到哪，切过去就该是那一片天。包详情页是单包视角，而宇宙画的是全骨架 3,375 个节点，从包页进来会没有「当前地址」可对。入口常量 `treeUniverseKey`，`Icons.blur_on`。

**采样面板加了开关**：`SpikeSceneView.showReadout` 默认 `false`，产品入口不传、看不到 `P50` / `P95`；`spike_main.dart` 显式传 `true`。默认关而不是默认开 —— 忘记传参的那一侧要落在安全的一边。验收口径不变：帧率仍只在调试入口采。

**半径常量收编**：`kInnermostShellRadius` / `kShellRadiusRatio` / `kShellCount` 三个已删，`sphere_shells.dart` 只留 `kAxisDepth` 与 `shellDepthForAxis`，半径一律走 `core/universe/placement.dart` 的 `shellRadiusOf()`。

### 未验

**「点进去能出、退出再进不崩」没有自动化用例守**：宇宙屏一构建就要 `gpuContext()`，widget 测试没有 Impeller 后端，会抛 `Flutter GPU requires the Impeller rendering backend` 并让整棵子树构建失败 —— 在那里断言「路由里有没有宇宙屏」，测到的只是环境限制。`TC-TREE-069` 因此只守「入口存在且唯一」，进出行为由终端 `flutter run -t lib/spike_main.dart` 与真机各看一次。

## B17b 笔 3：节点上球与轴色（本 ADR 修订十四）

笔 1 只产出坐标、一个点都没画，笔 2 只把星空挂进了产品。本笔把 3,375 个骨架节点里**当前这一屏该看见的那一组**画出来：当前节点、来路、直接子级。

### 绘制层：屏幕层，不进 3D 场景

节点画在 `SkyNodesPainter`，与星座连线同一层、同一个球心投影（`SkyProjection`），**不往场景里加几何实例**。

理由是笔 0 实测的结论：填充率不是瓶颈（像素翻 1.6 倍帧时间只涨 0.1 ms），而几何实例会直接把帧时间顶上去 —— 1,200 个 billboard 已经是当前唯一的几何负载。一屏一百来个点不值得去动它；而球心视角下半径不改变屏幕位置、只改变遮挡，屏幕层本来就不缺信息。

**代价**（登记为遗留）：屏幕层没有深度遮挡，来路的点与子级的点重叠时按绘制顺序压叠，不按半径。落在同一个屏幕上位置的两类点会互相盖住 —— 但落位本身已经把祖先放进顶部走廊、与子级不共格（`C-128` 的取舍），所以这只在极端视角下可见。

### 三轴三色与三档点径

一条路径只走一条轴（`SPEC-TREE-007`），所以**整幅视图取当前节点所在轴的那一色**，不逐点上色。三色（青 / 紫 / 金）留在 `features/palette.dart` —— 核心层不认颜色（`R1`），色值也不属于「可复算的量」。

点分三档：当前节点最大、来路次之、子级最小。子级最小是因为骨架最大同父有 105 个，同一档尺寸会糊成一片光。七个尺寸 / 透明度常量登记为 `C-134`–`C-141`。

### 落位坐标 → 投影方向

`SkyProjection.project` 吃的是**星表坐标系**（`x = cos(dec)cos(ra)`…），内部换成场景轴 `(x, z, y)`；而落位用的是「方位角 0 = 正前、仰角 0 = 水平」。两者差一个直角：相机 `yaw` 为 0 时视线正对方位角 0，而它对应的赤经是 90°。这个直角起了名字（`C-134`），不写成算式里的 `− 90`。

### 进视图：对准当前节点并停自转

当前节点在落位里的方位角与仰角都是 0，正好是 `yaw = 0 / pitch = 0` 的视线方向 —— 所以进视图时把相机摆到那里、并关掉自转。自转开着的话，几十秒后当前节点就自己飘出视野，而这一笔还没有任何标注（笔 5）能把它找回来。

摆位在 `initState` 做一次，不进 `build`：进 `build` 会每帧把用户刚拖出来的视角拽回去。

### 只画骨架；当前地址是载荷节点时上取

载荷节点（`system` / `planet`）没有球壳可上 —— `legalSkeletonSlots` 里不存在这两个槽位。所以：

- 子级列表里**过滤掉**载荷节点，否则 `layoutUniverse` 内部对槽位取层序时会抛；
- 当前地址落在载荷节点上时，沿来路**上取最近的、能上球的祖先**，结果记在 `UniverseView.anchorId`。

第二条是取舍不是遗漏：从「装饰器」切到宇宙，看见的是它挂靠的那颗骨架星及其兄弟，而不是一片空天。⚠️ 它同时也意味着 `anchorId` 可能不等于树屏那一行 —— 界面上要回答「你在哪一片天」，回答的是 `anchorId`。

### 已知边界（本笔不解决，登记在此）

- **进视图默认只看得见一部分子级**。子级仰角铺到 ±54°（`C-129` 的 120° 跨度），而 fov 70° 的垂半角只有 35°；方位角铺满 ±180°，而水平半角约 43°（16:9 视口）。实测口径见 `TC-UNIVERSE-008`：105 个里方位角在 ±90° 以内的 54 个在镜头前方，**在屏幕内的还要更少**。要看全子级得滚到 fov 110° 以上。改法是改网格或改默认视场角，两者都动 `C-127`/`C-129`，不在本笔。
- **没有标注**：光点不带名字，105 个子级在画面上无法区分谁是谁（笔 5）。
- **没有掌握度亮度**（笔 4）、**没有 LOD**（笔 6）、**没有虫洞过渡**（笔 7）。
- **实机未看**：本笔的观感（点径、三色在黑底上的辨识度、105 个点的糊度）只有真机才能判。
