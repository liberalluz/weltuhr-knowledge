# ADR-0002 · 开发顺序：纵切优先与风险前置

- **状态**：已接受 · **2026-10-17 修订**（见文末「修订」段，原文保留）
- **日期**：2026-10-17
- **决策人**：liberal

## 背景

设计基线已完成（8 份主题文档 · 171 条 `SPEC`，计数见 [`../design/00-index.md`](../design/00-index.md)），接下来要定的是**实施顺序**：先做哪一块、按什么粒度切批、什么时候承担技术风险。

两条既有约束决定了这件事不能随便排：

- [`00-index` §四的 X-05](../design/00-index.md)：验收须给**可观测断言**，「代码里写了」不构成证据。这意味着多数裁定只有在一条真实路径跑通后才能被验证，而不是读完规格就能确认。
- 主题域之间是**部分有序**：`FND` 是全员前置，`STEP` 依赖 `PLAN`，`QUANT` 依赖 `STEP` 的事件；但 `PACK`、`NOTE`、`GOV`、服务端彼此可并行。

## 决策

### 1. 批次按纵切推进，不按主题域分层做满

实施分为八个批次 B1–B8，每批以一道**出口闸门**（可观测判据）收尾，过不了闸门不进下一批。v0.1 的范围 = 最小可玩闭环的五个动作：

> 加载空间 → 圈定目标 → 建 Plan → 学一项 → 判合格写事件

**理由**：分层做满（先把 `VIEW` 的 34 条全部实现，再进 `PLAN`）会让最长一段时间里没有可运行产品；而 `X-05` 要求的断言大半要等整条链路走通才写得出来。纵切保证每一批都能给出**可跑、可看、可断言**的出口。

**代价**：v0.1 功能面窄 —— 无笔记、无治理、无跨设备；中期并行度低于分层推进（同一时刻只有一条主链在动）。

### 2. 投影可行性（W2-0）风险前置到 B2

自研 3D→2D 投影 + `Canvas` 批量渲染的帧预算，在**第二批**与事件内核并行验证，不等三视图正式开工。

**理由**：这是全案唯一可能**推翻实现方案**（而非仅调参）的未知。设计已排除三维引擎（`N-01` 禁力导向、`ADR-0001` 定 `Canvas` 级控制），若 150 项达不到帧预算，改变的是宇宙视图的实现路径而非某条规格；越晚发现越贵。

**边界**：风险前置 **不等于** 先做独立 spike。W2-0 的输入必须是 α 内容包（W8-4）的**真实图密度**，不能用随机节点 —— 合成数据的分布与真包差一个量级，得出的帧预算结论不可迁移。因此 W2-0 排在 α 包之后、仍在 B2 之内。

## 被否方案

| 方案 | 为什么否 |
|---|---|
| 分层优先：每个主题域做满再进下一个 | 前 60% 工期没有可运行产品；`X-05` 的断言大半要等整链路才能写，等于把验证全部堆到最后 |
| 独立 spike 先行：先拿随机节点验帧预算 | 无真实 pack 时，节点数 / 边密度 / 域分布全是编的，测出的帧率不能代表真实场景，可能白验一轮并误导实现方案 |
| 把排期落成 `docs/` 下的长期文档 | 排期是执行层、随每批闸门调整；与 `design/` 并存即成**第二真相源**（`design/` 改了它不会跟着改）。决策留 ADR、批次记 PR 描述即可 |

## 影响

- `docs/` **不新增排期目录**；批次划分与闸门记在对应 PR 描述里，本 ADR 只留决策与理由。
- W6 笔记 / W7 治理 / W9 服务端延后到 v0.2 / v0.3；Windows 单机首期**不依赖服务端**，W9 不在关键路径上。
- 每个里程碑仍是 1 个 PR（`W2` / `W4` / `W6` 各拆 2–3 个），合入即对账该批闸门。
- 客户端内核（事件流 / `fold` / 定位引擎 / 量化 / SRS）置于 `app/lib/core`，**禁止 import Flutter**，以便脱离 UI 单测 —— 这是纵切可行的前提。

## 修订 · 2026-10-17

> 以下五条为**本 ADR 实施一个批次后**的修订。原文全部保留（含已失效表述），修订只追加不改写 —— 读的人需要能看到「当初是怎么定的」。

### 1. 排期落点：从「只在 PR 描述」改为「`SDP` 承载」（实质修订）

**原文**（被否方案第三条）：「把排期落成 `docs/` 下的长期文档 → 排期是执行层、随每批闸门调整；与 `design/` 并存即成**第二真相源**（`design/` 改了它不会跟着改）。决策留 ADR、批次记 PR 描述即可」

**该理由只对 `design/` 成立，对 `deliverables/` 不成立。**

- `design/` 是活文档（不设版号、随讨论演进），在它旁边另立一份排期确实会成为第二真相源。
- `deliverables/SDP` 不同：**它本身就是排期的唯一权威处**，不存在「谁跟着谁改」的问题 —— 引用不复制即可。

因此现裁定：**决策与理由留本 ADR，排期由 `SDP` §4 承载，闸门的具体断言仍记对应 PR 描述**。原文那条理由相当于给「排期不落文档」这个降标做了合法性包装，属于错误论证，不因结论保留而变得成立。

### 2. 服务端版本：`v0.3.0` → `v1.1.0`（实质修订）

**原文**（§影响）：「W6 笔记 / W7 治理 / W9 服务端延后到 v0.2 / v0.3」

现分阶段为：`P1` 学习主链贯通 → `v0.1.0` · `P2` 笔记与治理 → `v0.2.0` · `P3` 上架与分发 → `v1.0.0` · `P4` 服务端与跨设备 → `v1.1.0`。

**服务端从 `v0.3.0` 移到 `v1.1.0` 不是勘误，是决策变更。** 依据是本 ADR 自身的「`W9` 不在关键路径上」：若上架必须等服务端，`W9` 就变成了关键路径，与本 ADR 直接矛盾。于是顺序改为**单机先上架**，服务端随其后。

原文的 `v0.2` / `v0.3` 同时是**两段式版号**，不符合本仓 `vX.Y.Z` 三段制，此部分属勘误。

### 3. 批次范围：`B1–B8` → `B1–B9`（实质修订）

**原文**（§决策 1）：「实施分为八个批次 B1–B8」

服务端独立成 `B9`（属 `P4`），故批次扩至 `B1`–`B9`。同时 `B7`（笔记与治理）归属 `P2`，编号在 `B8` 之前但属后一阶段 —— **编号不重排**，因为重排会让所有已讨论过的批次号失效。

### 4. 「1 里程碑 = 1 PR」→「1 批次 = 1 PR」（勘误 + 口径变更）

**原文**（§影响）：「每个里程碑仍是 1 个 PR（`W2` / `W4` / `W6` 各拆 2–3 个）」

这句话**自身矛盾**：既说「1 个 PR」，又说「各拆 2–3 个」。原意应是「每个里程碑的**每个批次**是 1 个 PR」。现统一为：

> **1 批次 = 1 PR**。批次是计划表的最小排期单位，一个里程碑可含多个批次。

`W2` / `W4` / `W6` 各拆 2–3 个，拆的正是批次，不是 PR。

### 5. `W` 编号不进入交付物（新增说明）

`W0`–`W10` 这套里程碑编号在本 ADR 与 `app/lib/` 的少量注释里过路使用，**但全仓没有任何地方定义过它**，`W0` `W1` `W3` `W5` `W10` 更是零出处。

`docs/design/00-index.md` §重编号 记录过同类事故（`Z1–Z4` 同时指视距档位与跨设备合并批次、`S1–S4` 与 FSRS 撞、`M1–M4` 与里程碑撞）。因此：

- `SDP` 与其余交付物**一律用交付物级名称**，不出现 `W` 编号。
- `W2-0` / `W8-4` 这类单点引用，在 `SDP` 中改写为描述性表述。
- `W` 编号只在本 ADR 内作为历史指称保留，不再扩展。
